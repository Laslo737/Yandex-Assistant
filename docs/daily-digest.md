# Ежедневный дайджест в Messenger

## Статус и формат

Production runtime **0eea730** (hotfix N+1 auth поверх 41ee813) выложен через постоянный путь; технические health,
admin auth и сохранность истории проверены. **Авторассылка пока выключена**:
в старой истории обнаружены два разных подтверждённых аккаунта, для пилота нужен
точный Messenger login владельца. Контакты массово не импортировались. Ручной
«Дайджест на сегодня» доступен для пользовательской проверки ссылок/формата.
Актуальные backup/rollback и результаты серверных post-checks — в `todo.md`.

Реализован в коде, **автоматическая отправка выключена по умолчанию**. Локальные
тесты не означают выкладку/проверку API Яндекса или успешную доставку 400 людям.
Расписание — понедельник–пятница, 09:00–10:30 **Europe/Moscow**, независимо от
часового пояса сервера. Производственный календарь/праздники пока не учитываются.

Одно короткое сообщение в личный чат бота:
- «Всего задач на мне» — все назначенные, включая завершённые;
- «С дедлайном сегодня» — только незавершённые, календарная дата по МСК;
- «Просроченные» — незавершённые с deadline раньше даты отчёта;
- «Обратить внимание» — до трёх разных задач с ключом-ссылкой и причиной выбора.

Все три метрики кликабельны. Фокус: сегодня → просроченные высокого/критического
приоритета → завтра → остальные высокого/критического приоритета. Внутри категории
приоритет убывает, затем более ранний deadline, затем ключ (детерминированный tie-break).
Поддержаны названия приоритетов на русском/английском и keys blocker/critical/high.
Нет искусственного наполнения до трёх задач. Нет поводов — спокойная строка;
активных задач нет — явное сообщение об этом. Отчёт отправляется и в такие дни.

LLM/комментарии/история изменений для рассылки не загружаются. Manager-блок не
добавляется автоматически. «Мой день» и ручной старый «Дайджест» не заменены.
Новый отчёт можно проверить командой **«Дайджест на сегодня»** или кнопкой в
**«Настройках дайджеста»**, даже пока scheduled-отправка выключена. Это ответ только
текущему подтверждённому пользователю, не broadcast и не запись об автоматической
доставке за день. Повторный ручной запрос может повторно загрузить данные.

## Получатели и права

`DIGEST_DB_PATH` — отдельная постоянная SQLite, **не** база аналитики. Реестр работает
при включённом Messenger независимо от `ENABLE_ADMIN` и `ENABLE_DAILY_DIGEST`.
Новые контакты регистрируются только после проверки личного чата и успешного
Messenger login → Tracker ID. Не собираются из групповых/системных сообщений,
`whoami` или ошибок identity. Регистрация первого контакта включает подписку;
такую политику автоматической рассылки нужно согласовать внутри компании.

Управление в боте: «Настройки дайджеста», «Отключить дайджест», «Включить дайджест».
Отписка сохраняется при следующих обращениях и импорте; отключить можно даже при
недоступном Tracker, в том числе первым сообщением до регистрации контакта. Опт-аут отменяет ожидающие/собирающиеся задания. Уже отправляемый
HTTP POST отозвать надёжно нельзя. Изменение Tracker ID у того же login автоматически
выключает подписку до явного включения. Контакты/предпочтения хранятся бессрочно;
таблица jobs очищается через 90 дней. Тексты отчётов и содержимое задач в ней не хранятся.

Перед каждым отчётом заново разрешается identity (общий безопасный кеш до 5 минут),
ID должен совпасть с сохранённым. Выборка проверяет точное `assignee.id`, проходит
все страницы и **поштучный ACL** до счётчиков/выдачи. Исключение ACL интерактивного
«Моего дня» сюда не переносится. Сбой ACL/API прерывает отчёт, не превращается в нули.
Чтобы сотни назначенных задач не вызывали сотни дополнительных HTTP-запросов,
дайджест запрашивает `createdBy/followers/access/components` вместе с остальными
полями через свежий `_search`. Каждая задача проходит тот же evaluator DENY/READ/
WRITE/roles/components; права пользователя и роли очереди читаются один раз на
очередь в пределах отчёта. Если проекция неполная (включая отсутствующие пустые
массивы), выполняется прежний GET auth-fields, без догадок о правах. Другие сценарии
и одиночный анализ остаются на прежнем пути; межотчётного кеша ACL нет.
Агрегат `tracker.batch_access` показывает checked/allowed/reused/fallback без ключей
задач и персональных идентификаторов. Это оптимизация загрузки, не отключение ACL.
Live-проверка на 728 назначенных задачах: вместо timeout на 60,7 секунды/386 HTTP
новый build собрал отчёт за 10,5 секунды/29 HTTP, 0 fallback GET/429/таймаутов.
Это один контрольный прогон на владельце, не гарантия скорости для 400 пользователей.

Задачи с компонентами остаются неподдержанными ACL и исключаются. Счётчики могут
отличаться от упрощённого «Моего дня» и UI Tracker; ограничения ACL описаны в `todo.md`.
Полная реальная ACL-матрица по-прежнему требует отдельной проверки.

### Импорт прежних пользователей

Не импортировать всю `analytics.users`: там есть неизвестные отправители/группы.
В предусмотренном CLI берутся только положительные свидетельства: `outcome=replied`
и известные сценарии, которые в текущем приложении выполняются после private/identity
gates (menu/my_day/team/changes/digest/issue_help/issue_analysis/risks/health/preview).
Диагностика/неизвестные/отказы исключаются. Каждая identity ещё раз проверяется через
Tracker перед регистрацией. Доступна только сохранившаяся история: старые удалённые
записи автоматически не восстанавливаются. Пользователь без такого свидетельства
будет зарегистрирован при следующем подтверждённом личном обращении.

После выкладки кода, с **выключенной рассылкой**, из постоянной production-папки:

```bash
cd /opt/yandex-360-ai-assistant
node dist/tools/digest-import-contacts.js
```

Ожидается `DIGEST_IMPORT_CANDIDATES: N` и `DRY_RUN`, без записи и без запросов к API.
После проверки политики импорта и backup:

```bash
node dist/tools/digest-import-contacts.js --apply
```

Ожидается `DIGEST_IMPORT_DONE: verified=N; unresolved=M`. Имена/секреты не печатаются.
Импорт не отправляет сообщения; повторный запуск не сбрасывает отписки. Между
получателями пауза 1 секунда, каждый lookup ограничен 30 секундами. Это отдельный
CLI-процесс со своим Tracker limiter: запускать в тихое окно, не параллельно с
scheduled-отправкой или нагрузочным тестом. При ошибке остановиться: импорт мог
частично сохраниться, но безопасно повторяем. Не восстанавливать данные из backup
поверх живой базы ради заполнения пропусков.

## Ссылки и дата отчёта

Используются общие builders в `src/shared/utils/tracker-query-links.ts`:
- точный исполнитель — подтверждённый Tracker login с конечным `@`;
- завершённые/отменённые статусы исключаются по каталогу, названия экранируются;
- «сегодня» → `Deadline: YYYY-MM-DD`, просрочка → `Deadline: < YYYY-MM-DD`;
- фиксируется дата отчёта по МСК, а не плавающее `today()` для старых сообщений;
- query URL кодируется и помещается в короткий `/r/:token`.

Токены теперь хранятся постоянно в `SHORT_LINKS_DB_PATH`, с 128 случайными битами,
не содержат URL в самом токене. Старые токены прежней in-memory версии после её
рестарта восстановить нельзя. Новые токены бессрочны: база содержит фильтры/login,
но не названия/тексты задач; включить её в политику персональных данных/backup.
Редирект публичный, данные самих задач защищает Tracker. Не публиковать SQLite/WAL
через nginx. Списки в Tracker живые, счётчик — утренний снимок: изменение назначения,
прав или статуса после отправки может изменить результаты. Конкретный синтаксис
нового date-фильтра и рендеринг ссылок проверить на реальном аккаунте перед рассылкой.

## Нагрузка и доставка

Один процесс приложения/одна организация/одна база. Несколько workers или второй
экземпляр бота с тем же токеном — не поддерживаемая схема масштабирования.
Не создавать дополнительный cron/systemd sender: scheduler стартует из `main.ts`
после начала прослушивания HTTP. `createApp()` сам не включает фоновые таймеры.

- Детерминированные слоты получателей распределены по 09:00–10:00, оставшиеся
  30 минут — запас на очередь/повторы. SQLite-очередь добавляет новые контакты
  примерно раз в минуту в пределах утреннего окна.
- Одновременно собирается **один** получатель. Между стартами минимум 10 секунд.
  Пер-user загрузка по умолчанию ограничена 60 секундами, включая очередь/identity/ACL.
- Фоновый HTTP использует максимум один Tracker-слот. Интерактивные запросы обгоняют
  фоновые; остальные слоты зарезервированы для них. Общие rate/cooldown/timeout
  действуют на оба класса. См. [tracker-load.md](tracker-load.md).
- Отправка Messenger последовательная, не чаще одного получателя за интервал;
  без `sendTyping`, без скрытого retry POST, с таймаутом до 12 секунд и не позднее
  конца утреннего окна. Правильный layout кнопок переиспользован из sender.
- Сбор данных может повториться до 3 раз с backoff. Полученный Messenger 429 —
  подтверждённый отказ: Retry-After учитывается и сохраняет глобальную паузу в SQLite.
  401 даёт общую паузу 5 минут; другие полученные 4xx отмечаются failed.
- Перед POST проверяются подписка, привязка identity и срок актуальности задания.
  При неопределённом результате POST (timeout/сеть/5xx) статус **uncertain**,
  автоматического повтора нет. Статус sent означает принятие HTTP-запроса API,
  не подтверждение прочтения сообщения. `payload_id` стабилен, но его идемпотентность не
  подтверждена; exactly-once не обещается.
- После рестарта просроченная lease безопасного этапа building позволяет пересборку;
  прерванный sending становится uncertain после lease, а не слепо пересылается.
  Уникальность login+дата препятствует повторной постановке завершённого задания.
- После 10:30 ожидающие задания истекают. Нет вечерней догоняющей рассылки и
  пачки вчерашних отчётов. При аварии/перегрузке доставка может быть пропущена.

**400 пользователей за 90 минут пока не подтверждены реальным замером.** Даже при
нулевом времени загрузки интервал 10 секунд требует около 67 минут на 400 стартов;
большое число страниц/ACL-проверок может не поместиться в окно. Не сокращать лимиты
вслепую. Сначала измерить пилот (`digest.build`: durationMs, trackerRequests,
tracker429, queueWaitMs; без содержимого задач), затем расширять. Фоновые отправки
не подделывают пользовательскую активность в аналитике: состояние доставки отдельно.

## Настройка и безопасное включение

Сначала согласованный staged deploy, backup, проверки тестов/health. Не делать pull,
npm ci или замену `.env` в работающем release. Рабочая папка пользователя — только
`/opt/yandex-360-ai-assistant`, см. `stable-working-path.md` и `deployment-safe.md`.
Серверный ключ бота/пароль/путь существующей analytics.sqlite не менять.

В серверном `.env` (пока флаг **false**):

```dotenv
ENABLE_DAILY_DIGEST=false
DIGEST_DB_PATH=/var/lib/yassistant/digest.sqlite
SHORT_LINKS_DB_PATH=/var/lib/yassistant/short-links.sqlite
DIGEST_ALLOWLIST=<точный Messenger login владельца>
DIGEST_MIN_INTERVAL_MS=10000
DIGEST_LOAD_TIMEOUT_MS=60000
```

Это **три разных файла** вместе с существующим `ANALYTICS_DB_PATH`. Каталог 0700,
владелец — фактический пользователь `yassistant`, файлы 0600/UMask=0077; проверить
systemd ReadWritePaths, если sandbox ограничивает запись. Не переносить локальные БД
или `.env` на сервер. Для Windows по умолчанию используются файлы в игнорируемом `data/`.

Отправка требует включённых Messenger/Tracker, соответствующих ключей и HTTPS
`APP_PUBLIC_BASE_URL`. Пустой allowlist **не позволяет включить scheduler**.
Сначала один точный Messenger login (не короткий Tracker login). Для всех — только
явное `DIGEST_ALLOWLIST=*` после успешного пилота и согласования политики рассылки.
Само присутствие в allowlist не создаёт контакт: пользователь должен обратиться
в личном чате или попасть в проверенный импорт.

Порядок пилота:
1. С флагом false зайти в бота → «Меню» → «Настройки дайджеста» → «Дайджест на сегодня».
2. Проверить все три ссылки и реальные выборки/даты; примеры нулей, завершённых,
   просроченных, нескольких приоритетов, ACL; целый отчёт на телефоне/desktop.
3. Проверить отписку, повторный заход (не включает её обратно), явное включение.
4. При необходимости выполнить dry-run/импорт старых контактов, как выше.
5. Отдельно включить флаг только для владельца, согласованно перезапустить сервис.
   В ближайший будний день проверить одну автоматическую отправку 09:00–10:30 МСК.
6. Рестарт, персистентность новых ссылок/настроек, отсутствие повторов; затем пилот
   5–10 человек. Только после замера расширять allowlist или выбирать `*`.

Проверки без вывода персональных данных:

```bash
cd /opt/yandex-360-ai-assistant
node dist/tools/digest-status.js
journalctl -u yassistant -n 100 --no-pager | grep -E 'digest\.(build|delivery|scheduler_failed|initialization_failed)'
```

`digest-status` читает БД read-only: число подписчиков, состояния jobs за неделю,
безопасные коды ошибок. Проверять sent/expired/failed/uncertain; частые expired
означают, что окно/бюджет не справляются. Перед публикацией журналов убедиться,
что сторонние строки/секреты не попали в вывод.

Отключение: поставить `ENABLE_DAILY_DIGEST=false` в серверном `.env` и выполнить
согласованный restart. Уже отправленные POST не отменяются. Предпочтения и ссылки
сохраняются. **Не удалять digest.sqlite:** потеряются отписки и журнал доставки,
что может привести к повторной отправке в тот же день. Ошибки storage не должны
отключать обычный бот при выключенной отправке; при включённой невалидная
конфигурация/недоступный delivery store останавливают startup с безопасной ошибкой.

## Backup / restore и ограничения

Существующий analytics timer **не включает автоматически** новые digest/short-links
БД. До массового включения добавить их в согласованный consistent backup/rotation и
restore-проверку; текущий timer не переустанавливать вслепую. Generic helper умеет
делать SQLite snapshot этих файлов без открытия application stores:

```bash
# Каждый destination должен быть новым файлом в защищённом каталоге backup.
node dist/tools/analytics-backup.js /var/lib/yassistant/digest.sqlite /защищённый/каталог/digest-YYYYMMDD.sqlite
node dist/tools/analytics-backup.js /var/lib/yassistant/short-links.sqlite /защищённый/каталог/short-links-YYYYMMDD.sqlite
```

Не копировать только `.sqlite` живого процесса — транзакции могут быть в WAL.
Восстановление только при остановленном сервисе, с сохранением прежних DB/WAL/SHM
и проверкой прав/целостности. Восстановление старого delivery snapshot может
откатить сведения об отправленных сообщениях/отписках: сначала выключить отправку,
сверить состояние за сегодня, не включать повторно вслепую. Новые short links,
созданные после snapshot, в восстановленной копии отсутствуют.

Базы содержат персональные login/ID/время и фильтры. Хранение, доступ, удаление по
запросу и внешние backup согласовать с компанией. Новая рассылка не исправляет
прежние открытые вопросы защиты webhook и ACL компонентов; это отдельные задачи.
