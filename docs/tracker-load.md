# Устойчивая загрузка Tracker — первая итерация

## Что реализовано

1. Данные интерактивного «Моего дня» кешируются на 60 секунд после успешного завершения загрузки. Ключ включает подтверждённый Tracker user ID, Messenger login и проверенный assignee login. Кеш отдельный для экземпляра сервиса/организации, не общий для разных людей. Ошибки и просроченные результаты не выдаются из кеша.
2. Повторные одновременные загрузки одного ключа объединяются (single flight). Каждый клик остаётся отдельным обращением/ответом, но не отдельной загрузкой списка задач. Возвращаются независимые копии, чтобы форматирование/вызывающий код не мутировали кеш.
3. Кеш ограничен 512 результатами (LRU); одновременно не больше 100 уникальных загрузок «Моего дня». Повторные ожидающие одного ключа не занимают новые загрузочные места. Это не ограничитель числа сообщений/ответов и не антиспам.
4. Дайджест и другие вызовы с проверкой ACL НЕ используют упрощённый интерактивный кеш; их права проверяются заново. Существующее исключение per-issue ACL интерактивного «Моего дня» осталось прежним. Кеш не повышает уровень безопасности этого исключения: отзыв назначения/смена содержимого могут быть не видны до истечения TTL. Для строгой модели доступа нужен отдельный пересмотр «Моего дня»; для production можно отключить хранение результатов TTL=0.
5. Identity gate перед сценарием сохранён. Одновременные lookup одного Messenger login объединяются, успешное сопоставление по-прежнему кешируется на 5 минут (bounded 512). Неопределённая identity и ошибки не кешируются. Перегрузка не маскируется под неверный аккаунт. Первая загрузка справочника статусов Workday и справочников очередей/статусов manager service тоже объединяется, без кеширования отказов.
6. В ответе «Моего дня» показано время завершения загрузки в UTC, одинаковое для повторных ответов из кеша. Это время сборки, не атомарный снимок Tracker и не обещание, что источник не изменился. Форматирование и short-links делаются заново, сами URL в кеш данных не сохраняются.

## Диспетчер HTTP

Все методы `TrackerApiClient`, включая пагинацию и auth endpoints, используют один lazy process-wide `TrackerTransport` и FIFO `TrackerDispatcher`. Нет второго слоя retries через прежний `shared/utils/http.ts`; он остался у Messenger. Общие лимиты относятся к этому процессу и **не ко всем приложениям, использующим OAuth-токен**. Несколько процессов/серверов имеют независимые лимиты; при масштабировании нужна координация либо разделение бюджета.

Начальные настройки (не подтверждённые квоты Яндекса):

| Переменная | По умолчанию | Значение |
|---|---:|---|
| `TRACKER_CONCURRENCY` | 4 | Одновременно активные HTTP-попытки |
| `TRACKER_MIN_INTERVAL_MS` | 150 | Минимум между стартами попыток, примерно не больше 6,7/с |
| `TRACKER_MAX_QUEUE` | 200 | Ожидающие HTTP-попытки, сверх активных |
| `TRACKER_QUEUE_TIMEOUT_MS` | 15000 | Максимум ожидания допуска одной попытки |
| `TRACKER_REQUEST_TIMEOUT_MS` | 12000 | Максимум попытки, включая чтение тела ответа |
| `TRACKER_OPERATION_TIMEOUT_MS` | 30000 | Бюджет одного HTTP-вызова со всеми ожиданиями и повторами |
| `TRACKER_MAX_RETRIES` | 2 | До двух повторов на 429: максимум 3 попытки |
| `MY_DAY_CACHE_TTL_MS` | 60000 | TTL успешного результата; 0 отключает хранение, single flight остаётся |
| `MY_DAY_CACHE_MAX_ENTRIES` | 512 | Максимум результатов в памяти |
| `MY_DAY_MAX_PENDING` | 100 | Максимум уникальных интерактивных загрузок |
| `MY_DAY_LOAD_TIMEOUT_MS` | 45000 | Deadline загрузки данных «Моего дня» после identity/menu preparation |

Ограничение concurrency **не заменяет** ограничение частоты. На 429 применяется общая пауза, учитывается `Retry-After` (секунды или HTTP date); без корректного заголовка — exponential backoff с небольшим jitter. Повторная попытка встаёт в общую очередь, слот активного HTTP при паузе не удерживается. Уже запущенные запросы не отзываются только из-за чужого 429.

Повторяем только GET/HEAD и известные read-only POST `/v3/issues/_search`, `/v3/issues/_count`. Запрос создания отчёта не повторяется даже на 429, но вызывает общую паузу. Сетевые ошибки/5xx/таймауты автоматически не повторяются: сначала измерения, затем отдельная безопасная политика. Число повторов не умножается на старый HTTP helper.

Долгий `Retry-After` не заставляет пользователя ждать бесконечно: очередь/операция истечёт по своему бюджету, сама общая пауза сохранится. AbortSignal убирает запрос из очереди, отменяет native fetch и чтение тела; обещание caller тоже ограничено таймаутом. Тестовые fetch adapters должны поддерживать AbortSignal: если адаптер игнорирует отмену, диспетчер завершит ожидание, но не может физически остановить чужой код.

## Границы времени и сообщения пользователю

- Есть отдельные безопасные сообщения: перегрузка очереди, истечение ожидания, таймаут загрузки, исчерпанные повторы 429.
- 45 секунд — бюджет **общей загрузки данных интерактивного «Моего дня»**, а не всего webhook/ответа. Identity и подготовка меню выполняются до него, отправка Messenger — после. Они ограничены собственными механизмами, но суммарного deadline всей переписки пока нет.
- Последовательная пагинация других сценариев ограничена по каждому HTTP-вызову, не общей продолжительностью сценария. LLM execution/таймауты Messenger не изменены.
- Ожидание общей загрузки одного пользователя не отменяет её для остальных нажатий; используется собственный deadline общей загрузки.
- Старый webhook всё ещё отвечает HTTP 200 до обработки; перезапуск может потерять работу. Надёжная очередь webhook — отдельный бэклог, текущая очередь HTTP существует только в памяти.

## Метрики и админка

Новая схема аналитики — **SQLite user_version=2**. При первом открытии v1 выполняется аддитивная транзакционная миграция, старые записи сохраняются и помечены как «Не измерялось». Перед выкладкой на реальную базу сделать consistent backup, см. `admin.md`. Старый код аналитики v1 намеренно не принимает v2: для rollback нужна совместимая версия либо backup v1, не ручное удаление колонок.

История → «Загрузка» → раскрыть:
- источник данных **«Моего дня»**: свежая загрузка / из кеша / общая загрузка;
- HTTP-попытки к Tracker, включая повторные;
- ответы 429 и таймауты HTTP/очереди/операции;
- сумму ожиданий HTTP-очереди, сумму длительностей HTTP-попыток;
- ожидание общей загрузки (для follower).

Обзор → «Нагрузка и кеш»: агрегаты за выбранный период и количество измеренных обращений. `bot.activity` включает те же безопасные метрики. Сырые URL, тела ответов, тексты задач и токены в новые метрики не попадают. HTTP-ошибка transport содержит только статус.

**Как читать:**
- Весь общий сетевой труд записывается у инициатора загрузки. Другие ожидающие не добавляют те же API-вызовы ещё раз; у них source=shared и своё время ожидания. Так же общий lookup identity/справочников учитывается у инициатора.
- «Из кеша» относится к списку задач: вспомогательные identity/menu lookup могут всё равно обратиться к Tracker при истечении их TTL. Поэтому cache-hit не обязательно означает 0 HTTP за всё обращение.
- Суммы времени параллельных операций могут быть больше wall-clock длительности ответа. Их **нельзя вычитать** из неё для вычисления «чистого времени обработки».
- Эти агрегаты относятся к завершённым записанным обращениям. Не показывают live очередь и незавершённые операции; при отключённой/неисправной аналитике обращения не восстанавливаются. Диспетчер и кеш продолжают работать и при выключенной админке.
- Таймаут Workday, случившийся вне выполняющегося HTTP, виден как код `MY_DAY_TIMEOUT`, но не придумывает HTTP-таймаут, которого не было.

## Проверки и следующий шаг

Автотесты без внешнего API: TTL/LRU/ошибки cache, 50 одинаковых запросов → одна загрузка, 50 разных пользователей без смешивания, обход interactive cache для ACL-aware digest, concurrency/rate/FIFO/overflow, 50 HTTP-запросов, 400 запросов с явным отказом сверх bounds, отмена/таймауты, Retry-After/общий cooldown/no retry writes, миграция v1→v2 и сохранение метрик после рестарта.

Это **проверка механизмов, не нагрузочное испытание компании на живом Tracker**. Нужны отдельно:
1. Проверить Windows локально через тестового бота: повторные «Мой день», timestamp/source, ошибки и метрики.
2. На Ubuntu проверить backup/migration/restart, RAM и корректность ответов.
3. С разрешения и без чтения чужих данных выполнить ограниченный нагрузочный прогон: cold/warm cache, несколько страниц задач, manager-сценарии одновременно с «Моим днём», p50/p95, число API-попыток, 429, очередь и таймауты.
4. Подобрать параметры по фактическим квотам и задержкам, учитывать общий токен у других приложений.
5. Если on-demand API всё ещё слишком дорого — отдельно проектировать обновляемые снимки данных/права/синхронизацию. В текущую итерацию они не входят.
