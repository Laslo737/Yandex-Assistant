# Админка использования бота

## Статус и окружение

Первая read-only версия: `/admin`, `/admin/users`, `/admin/activity`. Выключена по умолчанию. Три экрана работают внутри Express, без frontend-сервера, CDN или новых npm-зависимостей. Настоящих имён API Messenger сейчас не предоставляет: показывается login отправителя.

Хранилище — встроенный `node:sqlite` (`DatabaseSync`). Локально проверено на Windows / Node.js 24.19.0. На сервере пользователя — Ubuntu 24.04.4 / Node.js 24.21.0; smoke test этого окружения ещё нужен. SQLite API в ветке Node 24 имеет версионные ограничения/экспериментальный статус в части выпусков и может выводить предупреждение: обновления Node проверять отдельно. Не подавлять все предупреждения процесса. Нативный npm-модуль не нужен, переносить `node_modules` между ОС нельзя.

Один процесс приложения на одну базу. Не запускать несколько workers/реплик с общей базой: при инициализации незавершённые события помечаются прерванными. Для нескольких экземпляров потребуется иная координация/хранилище.

С добавлением защиты нагрузки схема SQLite обновляется до **user_version=2** аддитивной миграцией. В «Обзоре» появился блок «Нагрузка и кеш», в истории — раскрываемая колонка «Загрузка». Перед обновлением существующей базы сделать backup. Поля метрик, смысл shared/cache, настройки диспетчера и ограничения: [tracker-load.md](tracker-load.md).

## Что измеряется

- обращения (сообщения/команды/кнопки), но не открытие чата и не прочтение ответа;
- пользователь по ID Messenger (fallback — нормализованный login), первое/последнее обращение;
- сценарий, результат, длительность обработки вместе с отправкой;
- случайный request ID и безопасный код ошибки, но не текст ошибки;
- median — среднее двух центральных измерений при чётном количестве; p95 — nearest rank. Незавершённые/прерванные обращения исключены;
- активные пользователи/действия/ошибки за скользящие 1/7/30 суток, время UTC.

Меню, диагностические обращения, отказы и неопознанные отправители тоже учитываются. Личность из webhook не является доказательством identity в Tracker. Защита webhook и существующее исключение ACL «Моего дня» не изменены. Система не доказывает полезность отправленного ответа, не распознаёт отсутствие данных по тексту и не записывает внутренний AI fallback как отдельную ошибку. Общий `SCENARIO_FAILED` означает ошибку сценария, а не точно установленную неисправность Tracker/LLM. Если исключение содержит корректный HTTP status, сохраняется код вида `HTTP_429`; timeout/abort и несколько сетевых кодов распознаются по строгому allowlist, без копирования message/URL/data. Для деталей нужен отдельный аудит instrumentation интеграций.

Дедупликация относится к **аналитике**: повторное событие с теми же идентификаторами не увеличивает счётчик в пределах retention. Это не надёжная очередь webhook и не гарантия однократного выполнения действий бота. Если провайдер не дал стабильного ID, текущая нормализация использует время — дедупликация повторной доставки не гарантирована. История до включения не восстанавливается.

`bot.activity` в серверном журнале содержит request ID, сценарий, результат, длительность, безопасный error code. Никакие тексты сообщений, задачи, их ключи, комментарии, токены или сырые исключения в новой аналитике не сохраняются. Существующие сторонние логи проекта не заменены и требуют отдельного аудита. Аккаунты и время обращений всё равно являются персональными данными: согласуйте доступ и срок хранения.

## Локальный запуск на Windows

1. Node.js 24, `npm ci`.
2. В локальном `.env`:
   ```dotenv
   NODE_ENV=development
   ENABLE_ADMIN=true
   ANALYTICS_DB_PATH=./data/analytics.sqlite
   ANALYTICS_RETENTION_DAYS=90
   ADMIN_USERNAME=admin
   ADMIN_PASSWORD=<отдельный пароль не короче 5 символов>
   ```
Минимум по просьбе пользователя — 5 символов. Для публичного сервера рекомендуется случайный пароль от 20 символов: минимальная длина не означает достаточную защиту.

3. `npm run dev`, открыть `http://127.0.0.1:3002/admin`.
4. Для входа используется браузерная HTTP Basic авторизация. Не переиспользовать пароль Tracker/SSH. Browser Basic не имеет надёжной кнопки выхода: для работы удобно отдельное приватное окно, после работы закрыть его целиком. Форма входа/сессии — возможный следующий этап.

Данные в `data/` игнорируются Git. Не передавайте локальную базу в production. Приложение слушает loopback; локальный HTTP допустим только для разработки.

## Подготовка Ubuntu (не выполнять без проверки фактической конфигурации)

Проверенное имя сервиса: `yassistant`. Посмотреть фактического пользователя и ограничения:

```bash
systemctl show yassistant -p User -p Group -p WorkingDirectory -p ReadWritePaths -p ProtectSystem
systemctl cat yassistant
```

Не присылайте Environment/секреты из unit в чаты. Если User пустой, процесс работает как root — желательно отдельно перевести на выделенного пользователя после проверки прав всего приложения. Не менять пользователя вслепую вместе с выкладкой админки.

Создать `/var/lib/yassistant` с правами `0700`, владельцем сделать **фактического пользователя сервиса**. Если systemd ограничивает запись (`ProtectSystem` и т. п.), разрешить запись только в этот каталог через `ReadWritePaths`. Для файлов процесса рекомендуется `UMask=0077` в override unit; после изменения `systemctl daemon-reload`.

В серверном `.env` (не коммитить):

```dotenv
ENABLE_ADMIN=true
ANALYTICS_DB_PATH=/var/lib/yassistant/analytics.sqlite
ANALYTICS_RETENTION_DAYS=90
ADMIN_USERNAME=admin
ADMIN_PASSWORD=<новый случайный секрет>
APP_PUBLIC_BASE_URL=https://<фактический-домен>
NODE_ENV=production
```

Генератор пароля (результат не присылать):

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

Пароль хранится в `.env`, а не Git/URL/HTML; ограничьте чтение `.env`. По умолчанию сохраняются 90 дней событий. Очистка запускается при старте и обращениях, не чаще раза в час; при простое без запросов немедленного удаления по таймеру нет. У активного пользователя first_seen сохраняется как историческая дата; учётная запись удаляется после истечения retention без активности. SQLite может удерживать освобождённые страницы/данные в файле и WAL: это логическое удаление, не гарантированное физическое стирание; политика backup должна учитывать retention отдельно.

### nginx и HTTPS

Приложение оставить на `127.0.0.1:3002`. Существующий HTTPS reverse proxy может обслуживать `/admin` без отдельного upstream. Если nginx пропускает только отдельные пути, добавить location:

```nginx
location /admin {
    proxy_pass http://127.0.0.1:3002;
    proxy_set_header Host $host;
    proxy_set_header Authorization $http_authorization;
}
```

Basic проверяется самим приложением и на страницах, и на CSS/неизвестных путях. Не публиковать upstream-порт наружу. HTTP на публичном домене должен перенаправляться на HTTPS **до** приложения; `APP_PUBLIC_BASE_URL=https://...` проверяет конфигурацию, но сам TLS не включает. Не логировать Authorization. При необходимости ограничить `/admin` IP/VPN в nginx. Никаких routes для скачивания базы/backup нет. Интерфейс read-only, поэтому модифицирующих запросов в MVP нет.

30 неуспешных попыток в минуту на процесс: после этого для неверных credentials 429. Правильные credentials остаются доступны. Это базовая защита, не замена сетевым ограничениям. Security headers, escaping, no-store и CSP применяются к админке; секрет не попадает в HTML.

### Выкладка и проверка

1. Перед выкладкой — backup репозитория/конфига и базы (если уже есть).
2. В каталоге проекта: `git status -sb`, согласованное обновление кода, `npm ci`, `npm run build`.
3. `nginx -t`, reload nginx только если меняли конфигурацию.
4. `systemctl restart yassistant`, проверить `/health` и журнал без публикации секретов.
5. Без credentials `/admin`, `/admin/users`, `/admin/activity`, `/admin/theme.css` должны вернуть 401.
6. В приватном окне войти через HTTPS, проверить desktop и mobile, длинные логины, пустые периоды/фильтры.
7. Выполнить реальные обращения боту, проверить сценарий, результат, длительность, request ID в журнале.
8. Перезапустить процесс: история сохраняется; текущее прерванное обращение отмечается отдельно.
9. Замерить RAM/задержку бота до/после под ожидаемым количеством событий. SQL агрегаты синхронные, масштабировать только после измерений.

При отсутствующих/слишком коротких admin credentials или отсутствии HTTPS URL в production приложение останавливается с безопасной ошибкой конфигурации. Если база недоступна при инициализации, бот продолжает работу без аналитики, `/admin` возвращает 503. Если ошибка возникла позже, записи пропускаются с throttled `analytics.storage_failed`; пропущенные события не буферизуются и автоматически не восстановятся. После устранения проблем старта нужен перезапуск.

## Backup / restore

Ежедневный systemd backup (03:15 UTC, snapshots 14 дней), установка отдельно от release,
локальные проверки и ограничения: [ops/README.md](../ops/README.md). Установка timer
не считается завершённой до реального service backup и `AUTOBACKUP_READY` на Ubuntu.

Не копировать один `.sqlite` работающего приложения: актуальные транзакции могут находиться в WAL.

Из каталога проекта, под пользователем с правами на исходную базу и защищённый каталог backup:

```bash
node dist/tools/analytics-backup.js /var/lib/yassistant/analytics.sqlite /защищённый/каталог/analytics-YYYYMMDD.sqlite
```

Целевой файл не должен существовать. `VACUUM INTO` создаёт согласованный snapshot, включая committed WAL. На Ubuntu итоговые права backup `0600`; сам каталог должен быть `0700`. Команда не инициализирует AnalyticsStore и не помечает живые запросы прерванными. Планировщик/ротация и шифрованная внешняя копия настраиваются отдельно, срок хранения согласовать. Не размещать backup внутри веб-каталога.

Проверка backup: `PRAGMA integrity_check` через `node:sqlite` на копии, затем тестовый запуск с этой копией в изолированной среде. Не включать Messenger/Tracker для проверки восстановления.

Восстановление: остановить `yassistant`; сохранить текущую базу **вместе с WAL/SHM**; переместить их из рабочего пути; восстановить snapshot под именем основной базы, не оставляя старые WAL/SHM рядом; проверить владельца/права; запустить сервис и проверить данные. Никогда не заменять базу при работающем процессе. Перед rollback схемы проверять `PRAGMA user_version`; неизвестная версия намеренно не открывается сервисом аналитики.

## Как менять дизайн без разъезда

- `src/interfaces/admin/admin.theme.ts`: design tokens, сетки, breakpoints, стили компонентов.
- `admin.components.ts`: общий shell, навигация, escaping, формы, таблицы/статусы, даты, пагинация.
- `admin.pages.ts`: состав экранов, без копирования общего layout.
- `admin.router.ts`: read-only маршруты, валидация фильтров, авторизация/headers.
- `src/core/analytics`: типы сценариев/результатов, хранение и request-local telemetry отдельно от UI.

Новый сценарий добавляется в каталог типов и отмечается в реальном обработчике. Новая страница — независимая функция + маршрут + элемент общего navigation. Цвета/радиусы/отступы менять в токенах, не копировать inline-стили. Таблицы прокручиваются внутри карточки, не расширяют всю страницу. Поля используют отдельные control tokens для заметных рамок/фона и высоту 44 px; select имеет CSS-стрелку, все формы — явную кнопку сброса. Не ослаблять контраст рамок до уровня декоративных разделителей карточек. До 900 px навигация располагается сверху, до 480 px поля идут в одну колонку. После изменений проверять 320/390/768/1024/1440 px, keyboard focus, hover/active, отсутствие перекрытия контролов, длинные строки, пустые состояния, применение и сброс фильтров. Визуальная устойчивость требует регрессии, не обещание, что любой произвольный будущий HTML никогда не сломает дизайн.
