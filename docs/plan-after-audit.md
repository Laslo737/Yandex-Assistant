# План после аудита: подготовка к пилоту и продуктовый бэклог

Статус: проект плана для обсуждения. Это не обязательство реализовать всё сразу. Цель — сначала сделать существующие сценарии безопасными и заслуживающими доверия, затем добавить две новые функции с понятной пользой. Критерий успеха пилота: пользователь понимает, *что произошло, почему ему это показывают и какое действие требуется*, без риска увидеть чужие данные.

## Этап 0. Проверка предпосылок (до разработки)

- Уточнить модель доступа: в каких чатах работает бот; совпадает ли доступ сервисного OAuth-токена с доступом конкретного пользователя; можно ли проверять право пользователя на чтение задачи и её комментариев через Tracker. До подтверждения — не считать общий токен достаточной авторизацией.
- Проверить на реальных задачах API-пагинацию, полноту истории и поведение при изменении комментария без ожидаемого изменения `issue.updatedAt`.
- Согласовать 30–50 обезличенных кейсов для оценки: блокер, ожидание ответа, обещание выполнить действие, отсутствие оснований для вывода; получить оценку пользователей на полезность и точность.

## Этап 1. Исправления по аудиту — до платного пилота

### P0. Доступ и приватность

1. Проверять пользователя и его право на чтение задачи **до** загрузки/выдачи содержимого, включая разбор, preview, debug и ссылки на задачи. При невозможности надёжно проверить доступ — закрыть сценарий, а не полагаться на права общего токена.
2. Определить политику групповых чатов: чувствительные ответы только в личном чате, если нельзя гарантировать права каждого читателя. Отключить пользовательский доступ к debug-командам и исключить сырые ошибки/комментарии из ответов.
3. Зафиксировать, какие данные передаются внешнему LLM-провайдеру; минимизировать контекст, согласовать это с клиентом и предусмотреть отключение ИИ для организации.

**Готово, когда:** пользователь без доступа не получает содержимое задачи или выводы из него ни через одну команду; поведение личного/группового чата проверено тестами.

### P1. Честность и качество ответов

1. Убрать из меню обещание свободного Q&A, пока его нет; примеры вопросов должны реально работать либо быть заменены на поддерживаемые команды.
2. Разделять в ответе подтверждённый факт и гипотезу («вероятно»), показывать ссылку и основание важных выводов; не назначать владельца шага, если нет достаточных данных.
3. При сборке контекста учитывать значимые старые решения, а не только два последних комментария; исправить ключ кеша так, чтобы разные вопросы не получали один ответ и изменение комментария не оставляло устаревший ответ. Проверять ответы на согласованном наборе кейсов.
4. Пересмотреть сигнал «без движения» (`updatedAt` ≠ прогресс) и позиционирование health score: объяснять расчёт, настраивать пороги хотя бы для очереди, не выдавать эвристику за объективную оценку.

**Готово, когда:** вопросы с разной формулировкой получают релевантные ответы, в тестовых кейсах нет уверенно выданных неподтверждённых выводов, пользователь может открыть основание вывода.

### P1. Надёжность и стоимость

1. Устранить повторную загрузку bundle в «Помощи с задачей»; ограничить объём/параллелизм обращений к Tracker и LLM, добавить таймауты и метрики ошибок/задержки.
2. Обеспечить надёжную обработку webhook: события не теряются после HTTP 200 при рестарте или временном сбое; обработка идемпотентна, возможен повтор.
3. Для сводок и рассылок перейти от полного чтения всех очередей на каждый запрос к обновляемым данным/снимкам с отметкой времени актуальности. Планировать это по измерениям на пилоте, а не строить большую инфраструктуру заранее.

**Готово, когда:** повторная доставка безопасна, временный сбой не теряет событие, время ответа и число API-вызовов измеряются.

### P1. Выполнить обещание текущего MVP

Запустить **один** настраиваемый ежедневный дайджест в личный чат: участники, время и часовой пояс, отключение/пауза, только новые и значимые сигналы. Не рассылать пустые или повторяющиеся сообщения. Еженедельный health check — после проверки полезности ежедневного сценария.

**Готово, когда:** рассылка приходит вовремя, не дублируется после сбоя, выключается пользователем/администратором; источник и актуальность данных видны.

## Этап 2. Новый бэклог — после этапа 1

### B1. «Что требует моего решения?» (первым)

**Для кого:** владелец очереди/руководитель с подтверждённым доступом. **Ценность:** вместо перечня проблем — конкретные решения, без которых работа стоит.

**MVP:** по задачам доступных очередей находить явные запросы на решение/согласование и незакрытые блокировки. Выдавать максимум 3–5 случаев: задача и ссылка, что надо решить, кто ждёт, свидетельство (комментарий и дата), длительность ожидания **если она достоверно определена**. Кнопка «открыть задачу»; без автоматических изменений в Tracker. Если решение уже принято в последующей переписке — не показывать случай. Неизвестный адресат или спорный вывод — не выдавать как факт.

**Как внедрять:** сначала по запросу; затем, только при пользе на пилоте, добавлять в дайджест при появлении нового случая. Собирать обратную связь «полезно / неактуально / неверно» и не повторять отклонённое без новых событий.

**Готово, когда:** в проверочных кейсах нет закрытых или не относящихся к руководителю «ожиданий»; каждый пункт объясним и ведёт к конкретному решению.

### B2. «Кому и о чём напомнить?» (после B1 или параллельно при наличии ресурсов)

**Для кого:** сотрудник по доступным ему задачам. **Ценность:** быстрее возобновить зависшую коммуникацию, не перечитывая длинную историю.

**MVP:** показывать максимум 3 актуальных ожидания ответа/действия: от кого ждут, о чём, с какого момента и на основании какого сообщения. Предлагать короткий **черновик** вежливого напоминания, который пользователь проверяет и отправляет сам; без автоматической отправки и массовых уведомлений. Если адресат или вопрос не подтверждаются историей — не создавать черновик с выдуманными деталями. Учитывать последующий ответ и обещание автора самому выполнить действие, чтобы не напоминать не тому человеку.

**Как внедрять:** сначала по запросу в личном чате; проактивно предлагать только по явному согласию, после оценки точности и частоты ложных срабатываний.

**Готово, когда:** пользователь понимает основание напоминания, может отказаться без побочных действий; тестовые случаи с уже полученным ответом или сменой владельца шага отфильтрованы.

## Порядок и границы

`Проверка доступа и данных → P0 → честный интерфейс и оценка качества → надёжность + ежедневный дайджест → B1 → B2`.

Не включать в этот план универсального агента, автоотправку сообщений или автоизменение задач. После проверки предпосылок скорректировать объём и критерии, если Tracker не позволяет надёжно подтвердить права пользователя или историю событий.
