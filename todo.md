## 1. Коротко: что мы делаем

Мы делаем **AI copilot for Yandex Tracker** для **руководителей, team leads и project/delivery managers**.

Это **не замена Tracker** и не "универсальный AI для всей компании".
Yandex Messenger сейчас рассматривается как **первый интерфейс** к продукту.

Главная идея продукта:
- не просто показывать задачи;
- не просто строить сводки;
- а **быстро объяснять руководителю, что в Tracker идет не так: где риски, где зависания, где bottlenecks и что делать дальше**.

Ключевая ценность:
- **manager-facing visibility layer поверх Tracker**;
- **человеческие сводки и диагностика процессов**;
- **разбор конкретных проблемных задач**;
- **прямой переход из ответа в реальные задачи и выборки Tracker**.

Текущий честный уровень продукта:
- **pilot MVP / early product**;
- правильнее называть это сейчас **AI copilot for Yandex Tracker**, а не полноценной AI-platform и не generic AI-assistant для всей компании.

## 2. Новый зафиксированный продуктовый фокус

На текущем этапе продукт собираем вокруг **одного понятного manager-facing ядра**, а не вокруг абстрактного "AI assistant".

### Главный продуктовый тезис
Мы делаем **AI copilot для руководителей в Yandex Tracker**:
- показывает **риски, зависания и bottlenecks**;
- дает **человеческую сводку по состоянию работы**;
- помогает **разобрать конкретную проблемную задачу**;
- ведет **сразу в нужные карточки и выборки Tracker**.

### 1. Риски по очередям / AI-анализ процессов
Это **главный hero-сценарий продукта**.

Идея:
- система анализирует Tracker;
- находит перегруз, зависания, лишние согласования, рост времени ответа, проблемные команды и узкие места;
- формирует **управленческий вывод человеческим языком**, а не просто список метрик.

Пример целевого сценария:
- `За неделю:`
  - `18 задач зависли более 10 дней`
  - `Самая перегруженная команда — разработка`
  - `Иван держит задачи в статусе «В работе» в среднем 16 дней`
  - `43% задач проходят через лишнее согласование`
  - `Среднее время ответа выросло на 37%`

### 2. Сводка руководителя
Это **второй обязательный hero-flow MVP**.

Идея:
- руководитель открывает чат и за 30–60 секунд понимает, **что важно сегодня**;
- без тяжелых дашбордов и без ручной аналитики;
- ответ должен быть insight-first и вести в конкретные задачи.

Пример:
- `Что произошло за вчера?`
  - `Закрыто 84 задачи`
  - `Просрочено 7`
  - `Создано 26`
  - `CRM отстает на 5 дней`
  - `QA простаивает`
  - `Главная проблема — согласование дизайна`

### 3. Анализ конкретной задачи
Это **обязательный drill-down слой продукта**.

Идея:
- если в сводке или анализе виден риск, пользователь сразу проваливается в `Анализ <KEY>`;
- система объясняет, что произошло по задаче, почему она не движется, кто владеет следующим шагом и что делать сейчас.

### Что не делаем центральным promise прямо сейчас
- **универсальный AI-assistant по любым вопросам**;
- **AI для всей компании**;
- **большой AI-поиск по всему Tracker**.

Это остается важными направлениями roadmap, но **не является центром MVP-позиционирования**.

Важно:
- при этом **не теряем текущую сильную сторону проекта** — ссылки на задачи и на готовые списки задач в Tracker;
- пользователь должен сразу проваливаться из ответа в Tracker.

`AI-поиск по Tracker` и `универсальный assistant` остаются стратегическими направлениями, но **не должны размывать MVP-питч и текущую разработку**.

## 5. Новый MVP-фокус

### Базовая гипотеза
Самый сильный следующий шаг — собрать **понятный manager-facing MVP из трех сценариев**:
1. **Риски по очередям / AI-анализ процессов**;
2. **Сводка руководителя / Что важно сегодня**;
3. **Анализ конкретной задачи**.

После этого:
4. перевести сильные сценарии в **утренние / вечерние / недельные рассылки**;
5. только затем аккуратно расширяться в **AI-поиск по Tracker** и ограниченный assistant-слой.

### Почему так
Потому что это:
- дает реальную ценность руководителю;
- выглядит как понятный продукт, а не как vague AI-бот;
- легче продавать и пилотировать;
- меньше похоже на дублирование встроенных функций Tracker;
- лучше доказывает ценность через конкретный outcome: **быстро понять, где реально горит**.

### P1. AI-поиск по Tracker
Это стратегически сильное направление, но **не ближайший product wedge**.

#### Важная техническая оговорка
Полноценный AI-поиск и будущий assistant по всему Tracker **не должны** строиться на live fan-out по API при каждом вопросе.

Зафиксирован целевой технический подход:
- initial sync данных Tracker в локальное хранилище;
- incremental sync только изменившихся сущностей;
- хранение нормализованных `issues / comments / changelog / users / queues / projects`;
- derived-слой с signals / snapshots / facts;
- hybrid retrieval:
  - structured filters для operational Q&A;
  - keyword/full-text retrieval;
  - semantic retrieval;
- LLM использовать не как "базу данных", а как summarizer / explainer / synthesizer поверх уже отобранного context.

Это направление признается правильным и перспективным, но **сейчас сознательно откладывается** до тех пор, пока не будут добиты более простые и дешевые по сложности product wins.

#### Цель
Сделать поиск и ответы по естественному языку:
- по задачам;
- по комментариям;
- по истории изменений;
- позже — по связанным документам.

#### Первая версия
Минимальный scope:
- [ ] найти релевантные задачи по вопросу
- [ ] найти релевантные комментарии
- [ ] собрать candidate context
- [ ] сформировать краткий ответ
- [ ] показать источники / ссылки

#### Примеры первых supported questions
- [ ] `Как мы решали проблему с интеграцией SAP?`
- [ ] `Где обсуждали релиз CRM?`
- [ ] `Какие были похожие инциденты?`
- [ ] `Что уже пробовали по этой проблеме?`

#### Важное решение
- [ ] Для этого сценария, скорее всего, уже понадобится LLM + retrieval слой.
- [ ] Когда дойдем до реализации, отдельно спроектировать lightweight RAG для Tracker.

#### Какие вопросы должен уметь закрывать
- [x] `Дай саммари по задаче <KEY>`
- [x] `Почему задача <KEY> не двигается?`

- [x] `Что уже произошло по задаче <KEY>?`
- [x] `Что делать дальше по задаче <KEY>?`

#### Источники данных для этого сценария
- [x] issue details
- [x] comments
- [x] changelog / история изменений
- [ ] связанные задачи / links, если они дают важный context

- [x] Не делать это как full-search по всему Tracker.
- [x] Для одной задачи допустим richer context loading прямо on-demand.
- [x] LLM здесь может реально дать сильную ценность: summary, diagnosis, next-step suggestion, explainability.
- [x] Этот модуль должен переиспользоваться во всех местах, где уже есть кнопки `Анализ <KEY>`.

### P2. Универсальный AI Assistant
Это большой продуктовый вектор, который собирается из предыдущих модулей.

#### Важное ограничение по этапности
Сейчас **не** пытаемся сразу делать assistant по всему Tracker с ответами на любые вопросы через прямой live-разбор всех задач.

Сначала нужно:
- добить простые manager-facing и operational сценарии;
- собрать полезные deterministic tools и query handlers;
- подготовить foundation для локальной памяти по Tracker;
- только потом возвращаться к assistant-слою поверх всего массива задач, комментариев и changelog.

#### Идея
Пользователь пишет как человеку, а система:
- понимает интент;
- сама решает, какой сервис вызвать;
- отвечает либо фактом, либо сводкой, либо анализом.

#### Первые типы запросов
- [ ] `Что мне делать сегодня?`
- [ ] `Какие задачи просрочены?`
- [ ] `Что блокирует релиз?`
- [ ] `Кто самый загруженный?`
- [ ] `Почему проект задерживается?`
- [ ] `Дай саммари по задаче <KEY>`
- [ ] `Почему задача <KEY> не двигается?`

#### Практический подход
- [ ] На первом этапе не строить “магического общего агента”.
- [ ] Сначала сделать intent-based routing на ограниченном наборе сильных вопросов.
- [ ] Подключение LLM добавлять там, где rule-based логика уже не дает нормального UX.

## 7. Что делаем с ИИ

### Зафиксированная позиция
ИИ не надо подключать “ради галочки”.

Используем его там, где он реально усиливает продукт:
- суммаризация;
- формулировка управленческих выводов;
- объяснение причин;
- conversational Q&A;
- retrieval/RAG ответы;
- анализ большой собранной issue context.

### Практическое правило
- если задачу можно быстро и надежно решить rule-based / heuristic способом — сначала делаем так;
- если нужен качественный human-readable анализ или поиск по смыслу — подключаем LLM.

### Что уже заранее согласовано
- [x] Если для следующего этапа нужен LLM, пользователь готов подключить его через OpenRouter / ChatGPT-подобный стек.
- [x] Когда дойдем до конкретной интеграции, можно будет опереться на примеры из другого проекта.

### Вероятность подключения ИИ по направлениям
- `AI-анализатор процессов`:
  - первая версия: можно без LLM;
  - улучшенная версия: LLM очень полезен для summary/explanation.
- `AI-поиск по Tracker`:
  - почти наверняка нужен LLM + retrieval.
- `Универсальный Assistant`:
  - базовая intent-версия возможна без LLM;
  - сильная версия — с LLM.
- `AI для руководителей`:
  - базовый briefing можно собрать эвристически;
  - качественный executive summary лучше усилить LLM.

## 14. Product positioning на текущем этапе

Пока продукт нужно упаковывать так:
- **AI copilot for Yandex Tracker**
- **manager-facing visibility layer поверх Tracker**
- **сводка рисков, bottlenecks и зависаний для руководителей**
- **объяснение задержек, перегруза и блокеров с переходом в конкретные задачи**

- **AI-copilot для руководителей в Yandex Tracker: показывает риски, узкие места и зависшие задачи человеческим языком и сразу ведет в нужные карточки.**

Важно подчеркивать:
- это **не замена Tracker**;
- это **не generic AI-бот**;
- это слой, который помогает **за 30 секунд понять, что в Tracker реально идет не так**.

Пока не стоит упаковывать это как:
- full enterprise AI platform
- универсальный AI для всей компании
- "поболтайте с вашим Tracker"
- большой AI-search как уже готовый core use case

Это можно делать позже, когда появятся:
- реальный AI search,
- сильный conversational слой,
- proactive регулярный опыт,
- более устойчивый foundation.

## План: проверка доступа к задачам Tracker (актуальный приоритет; тестовая реализация в отдельной ветке)

### Контекст и зафиксированные решения

- Бот доступен сотрудникам организации через Yandex Messenger, Tracker вызывается одним сервисным OAuth-токеном. Доступ бота к задаче **не** доказывает право конкретного сотрудника видеть её. Индивидуальный OAuth сотрудника для этого продукта отвергнут.
- Ответы, содержащие данные задач, допускаются **только в личных чатах**. При обращении из группы — нейтральный отказ/приглашение в личный чат, без содержимого задачи. Для текущей проверки сохранён прежний режим webhook без секрета; это сознательно не решает задачу подтверждения отправителя. Организационная принадлежность и NDA не заменяют проверку доступа к каждой задаче.
- MVP: любую задачу с непустым `components` не обслуживаем, даже если запрашивает автор или руководитель; ACL компонентов пока НЕ реализуем. Если `components` не пришло либо структура непонятна, не считать его пустым: проверка не пройдена. Цена решения — ложные отказы для задач с компонентами; это сознательная граница первой версии.
- Действует fail-closed: невозможно достоверно подтвердить право — не показывать данные. Whitelist/`TRUSTED_FULL_ACCESS_USERS` не добавлять. `GRANT` не означает право чтения. `WRITE` на нужном уровне включает чтение. `DENY` имеет приоритет, включая получение через группу; не обходить его через роли задачи или исключения.
- Полный аудит продукта и дальнейший бэклог (включая «Что требует моего решения?» и «Кому и о чём напомнить?») — `docs/plan-after-audit.md`. Доступ к данным — prerequisite перед этими фичами и рассылками.

### Подтверждено реальными ответами API от пользователя (без хранения ФИО/ID в этом плане)

- `GET /v3/queues/{queue}/permissions/users/{userId}` возвращает `permissions.READ`, `.WRITE`, `.DENY`, `.CREATE`, `.GRANT` (верхний регистр), каждый с возможными `users`, `groups`, `roles`. Для одного пользователя подтверждён `DENY.users` при наличии `CREATE.groups`. У двух сотрудников с просмотром всей очереди есть `WRITE.users`, хотя отдельного `READ` в их ответах нет; у сотрудника с доступом только к своим задачам есть только `CREATE.groups`. Эти примеры не доказывают все возможные комбинации ACL.
- Проверен живой запрос `GET /v3/issues/{key}?fields=key,queue,createdBy,assignee,followers,access,components` на двух задачах IT: с компонентом пришёл `components: [{id,...}]` и заполненный `access`, без компонента пришли именно `components: []` и `access: []`; `queue.key`, `createdBy.id`, `assignee.id`, `followers[].id` присутствовали в обоих. Таким образом выбранная fail-closed проверка `Array.isArray(issue.components)` не блокирует подтверждённый кейс без компонента. Это не доказывает формат всех очередей/особых задач; проверять неожиданные ответы строго.
- `GET /v3/queues/IT/permissions` возвращает **нижний** регистр `read`, `write`, `grant`, `deny`. В показанной конфигурации IT: `read.roles` содержит `follower`, `write.roles` — `access`, `assignee`, `author`, `queue-lead`; `grant` сам по себе не используется как чтение. Массивы `groups`/`roles` могут отсутствовать вместо `[]`. ID ролей сравнивать по `id`, а не `display`; нормализовать регистр только в соответствующем адаптере.
- Обычный `GET /v3/issues/{key}` вернул `queue.key`, `createdBy.id`, `assignee.id`, `followers[].id`, `components[]`; при добавлении человека в поле «Доступ» появилось `access: [{id, ...}]`, до этого в полном ответе `access` отсутствовало. Показанная задача имеет непустой `components` и по MVP должна отклоняться. Для `fields=...` формат и отсутствие `access` при пустом значении ещё нужно проверить.
- Ответ сервиса под общим токеном НЕ является проверкой прав конечного пользователя. Документированного в рамках обсуждения issue-level effective-permission API для пары (user, issue) не подтверждено; собственная модель ACL — сознательный компромисс, не эквивалент Tracker ACL во всех будущих случаях.

### Согласованный алгоритм canUserReadIssue(userId, issueKey)

1. Проверить, что событие аутентично, это `private` chat, отправитель однозначно сопоставлен со **стабильным Tracker ID**. Нельзя брать `userId` из текста запроса или сравнивать ФИО. Иначе отказ без сведений о задаче.
2. Сервисным токеном получить только auth-поля задачи (`key`, `queue`, `createdBy`, `assignee`, `followers`, `access`, `components`) через `GET /v3/issues/{key}?fields=...`. Убедиться на живом API, что фильтрация работает. До проверки не вызывать LLM, загрузку комментариев/истории/вложений или user-facing форматирование; полученные auth-поля не выводить.
3. При 401/403/404, ошибке API, отсутствии очереди, неверном/неизвестном формате важных полей — fail-closed. Если `components.length > 0` — отказ. Отсутствие `access` трактовать как пустое **только после проверки** поведения Tracker для минимального GET.
4. Получить `/queues/{queue}/permissions/users/{userId}`; если effective `DENY` имеет непустые `users`/`groups`/`roles` — отказ. Проверить, что ответ относится к запрошенному пользователю; неожиданный формат — ошибка проверки.
5. Если есть `READ` либо `WRITE` через непустые `users` или `groups` в user-specific ответе — разрешить. `GRANT`, `CREATE` и одни только `roles` из этого ответа не считать общим доступом ко всем задачам.
6. Иначе определить роли по ID в auth-полях: `createdBy` → `author`, `assignee` → `assignee`, `followers` → `follower`, `access` с непосредственным пользовательским ID → `access`. Группы внутри `access` пока не поддерживаются (ложный отказ допустим).
7. Для найденных ролей получить `/queues/{queue}/permissions`. Разрешить только если фактический ID роли есть в `read.roles` либо `write.roles`. Не хардкодить правило «автор/исполнитель всегда может»; неизвестные ID/формат — fail-closed. Если роли не найдены — отказ без дополнительного запроса ACL.
8. Только после ALLOW загрузить полную задачу/комментарии/историю и формировать ответ. При отказе одинаковое нейтральное сообщение о недоступности/отсутствии задачи; при техническом сбое — «не удалось проверить доступ, попробуйте позже», без названия и других сведений о задаче. Во внутренних audit logs различать причину.
